Legacy data migration & cleansing

Excel HellDANTE · data assessment, normalisation, triage & enrichment

A wholesaler is replacing an ERP from 1996. Its master data lives in twelve spreadsheets that disagree with each other, and 80 percent of the project will be spent on them. So this is a pipeline that descends through nine circles of dirty data, repairs what it can prove, asks a human about what it cannot, and refuses to sign off when the numbers only look right.

The premise

Nobody writes bad data on purpose

Every defect in this repository is there because of something reasonable somebody did. A sales rep kept his own customer list because the ERP was slow. An export was latin-1 because it always had been. A postcode lost its leading zero the first time the file was opened in Excel, and a VAT number went into the company name because there was no field for it. Twenty years of that is what a migration actually receives.

The twelve files below are generated from a clean model and then deliberately degraded, so every planted defect is known. The engine never sees that record. It is what makes the detection rate on this page a measurement rather than a claim.

The descent

Nine circles, in dependency order

The circles are not decoration. You cannot match duplicates before the names are normalised, cannot reconcile before the money is parsed, and cannot check a foreign key before you know which records survived. So the engine runs I to IX, and each circle may rely on everything above it and nothing below it. Open a rule to see the real records it caught in this run.

The ninth circle

The data that is clean, loads fine and is still wrong

The deepest circle is reserved for betrayal, and in a migration betrayal looks like a reconciliation that balances. Two documents, two customers, one amount: one overstated by exactly as much as the other is understated. The grand total matches the legacy trial balance to the cent. Every row validates. The loader reports no errors, and the accountant finds it in March, when a customer disputes a statement and the old system is already switched off.

Every cent of the difference, attributed

A single net difference is useless, because a legitimate cause and a defect subtract from each other inside it. So each per-customer difference is attributed to a cause first, and the gate is held against what is left over.

The four gates

A gate does not describe the data, it decides whether the load may happen. Two of them fail, and failing here is the engine working.

What it does not catch

The detection rate, including the misses

Because the planted defects are known, recall is measurable per rule, and the test suite holds each rule to a floor. Some floors are deliberately well under 100 percent, with the reason written down next to them. A matcher that claims to catch every duplicate is lying, and a test suite that asserts it is helping.

The largest known gap is fuzzy name matching: a company shortened to its first and last word scores around 68, well below the auto-merge threshold of 92. Raising the threshold would merge a parent company with its subsidiary, which costs more than a missed duplicate. That trade-off is a business decision, so it is written in the registry rather than buried in the matcher.

Run it yourself

Three commands, no services

uv venv && uv pip install -e ".[dev]"

dante forge     # rebuild the twelve filthy source files
dante run       # descend, triage every row, evaluate the gates
dante report    # render the audit report

pytest -q       # 59 tests: parsers, recall floors, reconciliation

Everything is deterministic from one seed, so the numbers on this page are reproducible on your machine. The run exits non-zero when a gate fails, which is what makes it usable in a pipeline: a migration dry run that cannot fail is not a control.
